## Explicitly dropped (not vendored)

### From mattpocock/skills

| Skill | Why dropped |
|---|---|
| `ask-matt` | A router over Matt Pocock's own catalog, tuned to his skill names. `route` is this repo's equivalent for this catalog. |
| `setup-matt-pocock-skills` | Configures an external issue tracker (GitHub/GitLab/local) and a triage-label vocabulary. This repo has no external tracker; `CONVENTIONS.md` hardcodes the local equivalent instead of making it configurable. |
| `triage` | Moves issues through a state machine of triage roles. This repo's `Status:` vocabulary is lifecycle-only (`open`/`claimed`/`resolved`) with no triage roles, so there's no role vocabulary left for this skill to operate on. |
| `grill-me` | A one-line alias that calls the Skill tool with `grilling`. Once `grilling` is itself directly invocable, a thin alias just adds a near-duplicate description and routing noise. |
| `grill-with-docs` | Same alias pattern, calling `grilling` and `domain-modeling` together. Same reason: both targets are already independently invocable. |
| `improve-codebase-architecture` | Scans a codebase for deepening opportunities and produces a visual HTML report. A standalone audit tool, not a pipeline stage — out of scope for spec → tickets → execute → review, not a duplicate or tracker problem. |
| `resolving-merge-conflicts` | Resolves an in-progress git merge/rebase conflict. Useful, but orthogonal to the feature pipeline rather than a stage in it. |
| `prototype` | Builds a throwaway prototype to answer a design question. Referenced only as a ticket *type* inside `wayfinder` (the HITL "raise fidelity" case) — never vendored as its own skill; `decision-map` inlines the behavior as prose instead of calling out to it. |
| `handoff` (`claude-handoff`) | Its entire mechanism is spawning a background agent via `claude --bg` in the current directory. That launch pattern isn't wanted here; strip it and there's nothing left to adapt. |
| `teach` | Teaches the user a new skill or concept within the workspace. A tutoring skill, unrelated to engineering execution. |
| `research` | Investigates a question against high-trust sources and captures findings as Markdown. Same pattern as `prototype`: referenced as a `decision-map` ticket type, not vendored standalone — `decision-map` resolves research tickets directly or via an ad hoc sub-agent. |
| `wizard` | Generates an interactive bash wizard for steps only a human can perform (provisioning infrastructure, credentials, one-off migrations). Out of scope for this pipeline — it's not a spec/ticket/execution/review concern — but a plausible future add if infra- or credential-walkthrough work becomes routine. |
| `implement` | A nine-line skill: use `tdd`, run tests, use `code-review`, commit. Fully superseded by `subagent-execution`, which is that same loop automated and gated by review the original never had. |

### From obra/superpowers

| Skill | Why dropped |
|---|---|
| `brainstorming` | Explores user intent, requirements, and design before any creative work. Directly overlaps `grilling`/`decision-map`'s job; keeping it alongside them is the same near-duplicate-description problem as `grill-me`. |
| `writing-plans` | Writes a standalone plan file for multi-step work. A `.scratch` ticket is fed straight to a subagent as its task spec, with no plan-file layer above it — there's nothing left for `writing-plans` to produce that isn't already a ticket. |
| `executing-plans` | The non-subagent fallback for `writing-plans` output, run in a separate session. Depends on a skill not vendored here (`writing-plans`) and on worktrees (also not vendored); this repo always has subagent capability, so the fallback it exists for never applies. |
| `using-git-worktrees` | Creates an isolated git worktree per feature. Worktree isolation has repeatedly broken autonomous runs here — most likely its bundled dependency-install step — so `subagent-execution` uses a plain feature branch instead. Only its baseline-test-verification step (Step 3) was relocated into `subagent-execution`; the dependency-install step (Step 2) and all worktree-creation logic (Steps 0-1) were dropped along with the worktree model itself. |
| `finishing-a-development-branch` | Decides how to integrate completed work, with its logic built around detecting worktree state and shaping its menu around it. With no worktrees, most of its own rationale doesn't apply; `route`'s close stage (merge, cherry-pick durable decisions, delete `.scratch/`) replaces it directly. |
| `using-superpowers` | A session-start hook that injects "you have no choice, you must invoke a matching skill" into every session. This repo's skills are reachable by description match but never forced this way. |
| `dispatching-parallel-agents` | Generic guidance for running independent parallel agents. `subagent-execution` has its own narrower parallelism rules built in, and explicitly forbids parallel implementer dispatch (it causes conflicts) — a generic overlay skill isn't needed on top of that. |
| `verification-before-completion` | "No completion claims without fresh verification evidence." Its substance is already load-bearing inside `tdd` (mandatory Verify RED / Verify GREEN) and the reviewer templates ("Do Not Trust the Report"), rather than vendored as a separate general-purpose skill. |
| `receiving-code-review` | Confirmed during research to be referenced by nothing upstream either, even within superpowers itself — genuinely orphaned there. Its posture (verify before implementing suggestions) is folded into `subagent-execution`'s prompt templates instead. |
| `writing-skills` | Superpowers' own meta-skill for authoring skills in its conventions. This repo's `vendoring` skill is the equivalent for this catalog's actual need — pulling in upstream skills — so `writing-skills` itself doesn't transfer. |
| `systematic-debugging` | A hard-bug diagnosis loop that directly duplicates Pocock's `diagnosing-bugs`, which was chosen as the vendored one — keeping both is the same routing collision as `grill-me`. |
